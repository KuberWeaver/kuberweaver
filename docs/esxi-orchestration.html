KuberWeaver · Orchestration ESXi

Du wizard CLI au guest Ubuntu : templates, connecteurs, vault, saved plan OpenTofu + OVF Tool, état durable. Généré depuis le code source.

Où sont les fichiers

  • • Template VM : plugins/vmware-vm/main.tf + manifest.yaml
  • • Services : plugins/<brique>/*.yml, collections épinglées, roles.lock.json
  • • Presets : presets/zabbix-7.yaml · OVA : data/os-images/ubuntu-24.04
  • • Extensions : data/extensions/ (esxi-ovf, esxi-runtime, local-vault), source examples/extensions/
  • • Vault : data/local-bao (OpenBao raft) ou Fernet local-vault
  • • État durable : PostgreSQL + data/environment-state/state.key
  • • Plans et preuves OVF : data/plugin-data/esxi-ovf/states/<job-id>/

Séquence ESXi (saved plan)

  • • 1 wizard : lit catalogue + connecteurs, dry-run admission, crée le blueprint
  • • 2 deploy request : admission, pins de préparation, job en file (prepare)
  • • 3 worker : tofu init/plan/show sur main.tf, saved plan + digest
  • • 4 le plan revient en pending_approval (pas un succès)
  • • 5 approve : pins et plan revérifiés, commit GitOps, apply du plan exact
  • • 6-7 pont socket → ovftool (ticket clone, morefs) → reconfig → guestinfo cloud-init → power on
  • • 8 résultat et vérification de l’UUID enregistrés par job ; état de stack distinct

Services & cycle de vie

  • • 9 une brique = un job, sur guest existant (target_uuid + ssh_key_id), clé privée éphémère depuis le vault
  • • VM + service dans un même graphe : refusé par l'admission (mixed_profiles), le chaînage se fait entre jobs
  • • apply / verify / snapshot / rollback / remove par brique ; create-only OVF sans rollback
  • • Pour ce flux OVF, l’adoption relie le résultat du job à un état de stack. La décommission par stack vérifie la propriété et respecte la quarantaine.
  • • Logs par job (kw logs --follow), audit, finops sur ressources déclarées
Ce que le job prouve : ESXi a enregistré et démarré la VM, identifiée par son UUID. Le résultat indique séparément si VMware Tools a remonté une IP. Ni le statut du job ni une IP remontée ne prouvent une connexion SSH réussie. Le job Ansible suivant vérifie le service sur cette VM.

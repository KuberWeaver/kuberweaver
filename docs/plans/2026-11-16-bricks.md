# Bricks and stacks

Status: implemented for `web-nginx` (see `plugins/web-nginx`), proposed for the rest. Defines what a brick is, what a stack is, and how a full
application such as Zabbix is composed on a VMware guest without turning the
catalogue into a pile of bespoke scripts.

## The short answer

You do not deploy "nginx" or "Zabbix". You declare one or more **bricks** on a
target, and a stack is the graph of those bricks.

- `nginx` is one brick on one VM.
- `Zabbix` is four bricks on one or more VMs, linked by dependencies.

The operator sees either a preset (a saved graph) or individual bricks. Both are
data. Adding Zabbix adds no code path.

## What a brick is

A brick is a declaration that wraps an existing upstream Ansible role. It does
not reimplement the software, and it does not carry shell.

    id            web.nginx
    version       1.4.0
    kind          workload
    requires      compute.vm
    inputs        JSON Schema, same validator as the rest of the catalogue
    implementation
      engine      ansible
      source      geerlingguy.nginx  (pinned version, checksum recorded)
    verify        checks that prove the brick works, run after apply
    snapshot      paths captured before apply, to allow restore
    teardown      the exact inverse: services stopped, packages removed,
                  files removed, accounts removed

Rules that make a brick admissible:

1. **It wraps upstream.** The role comes from Galaxy or a pinned git ref. The
   brick adds contract, verification and inputs. Nothing else.
2. **It is pinned.** Role version plus checksum recorded in the plan. A brick
   that floats is not reproducible.
3. **It declares verification.** If the brick cannot prove it works, it is not a
   production brick.
4. **It declares its undo.** Snapshot and restore, or an explicit statement that
   it cannot be undone. Silence is not acceptable.
5. **It declares its data class.** `config` can be restored. `state` such as a
   database volume cannot be rolled back by the brick and says so out loud.
6. **Inputs are closed.** No free-form variables, no command, no playbook path,
   no password. Secrets are references to vault keys.

## What a stack is

A stack is a graph: bricks as nodes, dependencies as edges. Ordering comes from
a topological sort, which the catalogue already does.

    compute.vm  esxi-lab/kuberweaver-test
      └── web.nginx

    compute.vm  esxi-lab/zabbix-01
      ├── db.postgresql
      ├── monitoring.zabbix_server      requires db.postgresql
      ├── monitoring.zabbix_web         requires monitoring.zabbix_server
      └── monitoring.zabbix_agent       requires monitoring.zabbix_server

The same four bricks can also be spread across three VMs, because a brick names
its target. That is the whole modularity claim: composition changes, bricks do
not.

A **preset** is a saved graph with sensible defaults. "Zabbix 7 on one VM" is a
preset, not a new brick. Editing the preset produces a normal graph.

## Worked example 1: nginx on a VM

    id: web.nginx
    implementation:
      engine: ansible
      source: geerlingguy.nginx        # MIT, actively maintained
    inputs:
      server_name   string, required
      listen_port   integer, 1..65535, default 80
      document_root string, absolute path
      upstreams     array of {name, host, port}, optional
    verify:
      - service nginx is active
      - nginx -t succeeds
      - GET http://127.0.0.1:{listen_port}/ returns 200
      - the served page contains the configured server_name
    snapshot:
      - /etc/nginx
      - {document_root}/index.html
    teardown:
      - stop and disable nginx
      - remove the site configuration and the served page
      - remove the package only if no other brick claims it

Note on choice: `nginxinc.nginx_core` is the vendor collection but its last
release is roughly three years old. `geerlingguy.nginx` is the maintained
option. Record the choice and the reason in the brick, so the next person does
not relitigate it.

## Worked example 2: Zabbix, four bricks

    id: db.postgresql
    implementation: geerlingguy.postgresql (pinned)
    inputs: db_name, db_user, owner_password_ref (vault reference)
    verify: pg_isready, port 5432 listening, database and role exist
    data_class: state
    undo: restore from an external backup only; the brick refuses to pretend

    id: monitoring.zabbix_server
    implementation: community.zabbix.zabbix_server (pinned)
    inputs: db_host, db_name, db_user, db_password_ref, server_port 10051
    verify:
      - service zabbix-server active
      - port 10051 listening
      - zabbix_get -s 127.0.0.1 -k agent.ping returns 1
    snapshot: /etc/zabbix, /var/lib/zabbix
    data_class: config plus state

    id: monitoring.zabbix_web
    implementation: community.zabbix.zabbix_web (pinned)
    inputs: server_host, listen_port, tls (optional)
    verify:
      - GET / returns 200 and the page contains the Zabbix login form
      - php-fpm active
    snapshot: /etc/zabbix/web, nginx site configuration

    id: monitoring.zabbix_agent
    implementation: community.zabbix.zabbix_agent (pinned)
    inputs: server_host, hostname
    verify: port 10050 listening, agent.ping answered from the server

Two things this example settles:

- **A brick may consume another brick's output** through declared inputs, never
  by reaching into the guest. The database address is an input resolved from the
  graph.
- **Data is honest.** Postgres holds monitoring history. The brick can be
  removed; the data cannot be rolled back by the tool. That is declared, not
  discovered during an incident.

## How verification works

Every brick ships checks that are cheap, deterministic, and read-only:

- service state and unit health
- listening sockets
- an application-level probe (HTTP status, protocol ping)
- a content assertion where it proves something real (login form, version)

A brick that only checks "the package is installed" is a brick that does not
know whether it works.

Nightly drift for config bricks reuses the same mechanism: run the pinned role
in check mode with diff, and report what would change. Read-only, no remediation.

## Where this fits the existing code

- The graph, schema validation, policy admission, digest-bound approval and
  evidence already exist and are reused unchanged.
- The missing piece is one adapter: `workload` on `compute.vm`, executing a
  pinned role and then running the brick's verify checks.
- The constrained container executor stays as an example. It is not the model to
  generalize; this is.

## Order of implementation

1. `web.nginx` as the reference brick: smallest real surface, easy verification,
   immediate value.
2. `db.postgresql`, which forces the data-class decision honestly.
3. `monitoring.zabbix_server`, then `zabbix_web`, then `zabbix_agent`, plus the
   one-VM preset.
4. Only then consider clusters. Forty lines of brick contract beat a control
   plane you cannot verify.

## What must not be relaxed

- No brick executes free-form commands or an arbitrary playbook.
- No brick carries a secret; only a reference.
- No brick without verify, without undo statement, or without pinning.
- Presets are data. The moment a preset needs its own code path, the catalogue
  has failed.

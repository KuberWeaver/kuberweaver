KuberWeaver

One governed workflow from service catalogue to verified execution.

Self-hosted infrastructure management with a governed request workflow.

Install it Read the limits first

No Kubernetes required. No embedded AI model. The server binds to 127.0.0.1.

The problem

Infrastructure changes still happen through manual clicks, isolated scripts and private shell history.

When something goes wrong afterwards, three plain questions usually have no shared answer: who requested the change, who approved it, and which exact steps ran. There is no admission check before execution, no record that survives the session, and no evidence that what was deployed matches what was approved.

KuberWeaver exists to make those answers ordinary rather than heroic.

What KuberWeaver does

Each item below is implemented in the repository today. The boundary table further down states exactly how far each one goes.

Service catalogue

Services are described by declarative manifests and JSON Schemas. You compose a blueprint of resources and services, and the forms and validation come from the plugins rather than from hard-coded client branches.

Governed requests

An operator validates a plan, submits a request and waits. An administrator reviews the exact plan and approves it. Canonical hooks observe events but cannot replace validation or approval.

Verifiable execution

The lab Ansible executor runs backup, canary, verification, rolling deployment and final verification. Commit and HTTP evidence remain available after the job ends.

Durable environment state

One encrypted, generation-numbered record per environment and stack. An exclusive apply claim serializes operations, every authenticated call leaves an audit row, and a nightly read-only comparison reports drift without remediation.

Managed SSH keys

Keys are generated into the vault, selected for an operation, disabled on rotation and exported only explicitly. Connection secrets live in the secret source, not in command lines.

Revocable agent access

A human administrator issues tokens with a maximum role, explicit scopes and an expiry. Revocation blocks new requests immediately. MCP exposes typed domain tools, never arbitrary shell commands.

What it does / what it does not do

This table reproduces the capability boundaries of the project README. It is the most important section of this page because it defines the supported scope, the conditions and the known gaps.

Capability Supported scope and limits
Catalogue, blueprint storage and governed deployment Available through the API and the kw CLI.
Sessions, RBAC, CSRF, quotas and approval Local accounts plus an optional, disabled-by-default OpenID Connect sign-in that binds to an existing local account; no per-object authorization.
NGINX and Apache Real Ansible deployment on two allowlisted GNS3 guests, with HTTP verification.
Canary, rolling and rollback Exercised for managed web workloads; not a universal recovery guarantee.
VMware Ubuntu OVF import Create-only workflow documented separately; no update, deletion, rollback or automatic cleanup after an ambiguous failure. Target OS/SSH acceptance requires an authorized real import.
ESXi discovery Separate read-only provider; observed VMs are not proof of a running guest OS.
OpenTofu/libvirt and blank-disk vSphere blueprint Planned/disabled with documented transport and powered-off-create blockers; not promoted by the separate OVF workflow.
Redis persistence Service-specific lifecycle and restore tests; shipped manifest remains planned and runtime disabled pending real target acceptance.
Frontend/backend stack, Cisco IOS, pfSense and cloud entries Planned and disabled; no validated adapter/target path.
GitOps Local approved-plan commits; optional remote publication verifies the exact SHA. Test-repository evidence is not a hosted customer delivery pipeline.
FinOps Internal tariff estimates, not cloud billing or measured consumption.
Diagnostics Deterministic rules; optional LLM provider requires explicit configuration.
Notifications and ChatOps Durable outbox, webhook delivery and signed callback exercised locally; no certified Slack/Teams integration or configured external SaaS recipient.
Secrets Replaceable OpenBao and local Fernet providers; local custody and transport limits apply.
Execution credentials Operation-scoped injection, isolation and cleanup; does not imply existing lab keys were replaced.
External API/MCP clients Explicit role/scopes, expiry and revocation; no automatic approval.
Observability Local metrics and authenticated snapshot; validated rules/dashboard files do not mean a deployed Prometheus/Grafana stack.
Public marketplace, payments and untrusted-code isolation Not provided.

Two declarations deserve the same caution: disk_gb is a budgeting declaration, not an enforced disk quota, and public_cidr is an admission guard, not an installed firewall rule.

Contribute

Three ways to help, ordered by commitment.

1. Report a bug

Open an issue with the command, the input and the observed behaviour. Silent refusals and accepted bad input count as bugs, not as edge cases.

2. Write a plugin brick

A brick is one folder containing a manifest.yaml, its JSON Schema and the Ansible roles or playbooks. The kernel discovers it; you do not touch the core.

3. Write an extension

An independently installable Python package registers a provider or a canonical hook through the SDK. It is installed, checked by doctor, then enabled explicitly.

Read CONTRIBUTING.md for branches, checks and pull request rules.

Installation

The documented path uses uv and installs the kw CLI. Python 3.12 or newer is required.

The server listens on 127.0.0.1:8088. The documented installation uses user systemd units from ops/; they are not enabled automatically at boot, and the service is not meant to be exposed directly to the Internet.

FAQ

Is KuberWeaver production ready?

No. It is a prototype. The documented installation runs on workstation loopback for a lab, with local accounts and no high availability, SSO, multi-tenancy or sandboxed marketplace. Treat the capability boundaries as the authoritative scope.

Can I use KuberWeaver under a commercial license?

The project is GPL-3.0-or-later. A commercial license is available for organizations that cannot accept copyleft terms, and the terms are agreed with the maintainer before any derived product is distributed. This page does not grant any license and does not set pricing.

Does it require Kubernetes or an AI model?

No. KuberWeaver does not embed an AI model and does not require Kubernetes. An optional LLM provider can be used for diagnostics, but only when it is configured explicitly.
